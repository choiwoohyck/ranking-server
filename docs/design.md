# Design Decisions

## 0. 점수의 정의
- 선택지: A) 특정 게임 전용 점수  B) 범용 점수 (높을수록 좋은, 감소하지 않는 정수)
- 결정: B
- 이유: 특정 게임에 묶지 않고 어떤 클라이언트든 쓸 수 있게 함. 서버는 점수의 의미를 모르고 숫자만 비교함.
- 예시: 해달왕국 → 누적 획득 골드
  - 보유 골드는 제외: 건물 구매 등으로 소비하면 감소함. 최고 점수만 갱신하는 구조라 감소하는 값은 랭킹 의미가 없음.
- 바꿀 시점: 스테이지별 랭킹이나 클리어 타임처럼 낮을수록 좋은 기록이 필요해지면 리더보드 단위 + 정렬 방향 설정으로 확장.

## 1. 점수 저장 방식
- 선택지: A) 유저당 최고 기록 1개만  B) 제출할 때마다 전부 기록
- 결정: A
- 이유: 랭킹에 필요한 건 유저별 최고 기록 하나뿐임. 데이터가 유저 수만큼만 쌓이고 조회가 단순함.
- 바꿀 시점: 치팅 탐지가 필요해지면 B 추가. 제출 이력이 있으면 "짧은 시간에 비정상적으로 큰 증가" 같은 패턴을 잡을 수 있음.

## 2. 동점이면 누가 위인가
- 선택지: A) 먼저 달성한 사람이 위  B) 같은 순위로 표시  C) 신경 쓰지 않음
- 결정: A
- 이유: 대부분의 게임이 이렇게 동작함. 달성 시각도 의미 있는 기록임.
- 구현 영향: `Score`에 달성 시각 필드 추가. 같은 점수를 다시 제출하면 시각을 갱신하지 않음 (갱신하면 먼저 달성한 사람이 재제출만으로 순위가 밀림) → 점수가 "더 클 때만"(`>`) 갱신.

## 3. 정렬은 언제 하나
- 선택지: A) 조회할 때마다 정렬  B) 저장할 때 정렬된 상태 유지
- 결정: A
- 이유: 구현이 단순함. 출시 전이라 데이터가 적어서 성능 문제가 없음. 측정하기 전에 최적화하지 않음.
- 바꿀 시점: Day 11 k6 측정에서 랭킹 조회 p95가 기준(예: 200ms)을 넘으면 개선. 후보는 DB 인덱스, Redis Sorted Set. 개선 전후 수치를 기록함.

## 4. 같은 유저가 동시에 점수를 두 번 내면
- 선택지: A) 지금은 두고 Day 11에 테스트로 확인  B) 지금부터 ConcurrentHashMap + 원자적 갱신
- 결정: A
- 문제: "기존 점수 읽기 → 비교 → 저장" 사이에 다른 요청이 끼어들면 높은 점수가 낮은 점수로 덮일 수 있음.
- 이유: 메모리 저장소는 Day 3에 JPA(DB)로 교체되는 임시 구현임. 지금 메모리 저장소에서 해결해도 버려지는 코드가 됨. 실제 해결은 데이터가 저장되는 DB 계층에서 해야 함.
- 바꿀 시점: Day 3 DB 전환 후, Day 11에 동시 제출 테스트로 문제를 재현하고 DB 방식(락 또는 조건부 업데이트)으로 해결.

## 5. "최고 점수만 갱신" 규칙은 어디에 두나
- 선택지: A) Service에서 `if (new > old)` 비교  B) `Score` 안에 `updateIfHigher(newScore)`를 두고 setter 제거
- 결정: B
- 이유: setter가 있으면 어디서든 `setScore(0)`처럼 점수를 낮출 수 있음. 규칙을 객체 안에 두면 "점수는 낮아질 수 없다"를 `Score`가 스스로 지킴 (캡슐화).
- 구현 영향: setter가 없으므로 `Score`는 생성자로 만듦.

## 6. 배포 구조와 CI/CD

```
개발자 push ─▶ GitHub Actions
               ├─ test: MySQL 서비스 컨테이너 + ./gradlew test   (모든 브랜치·PR)
               └─ deploy: main 브랜치 + test 통과 시에만
                    1. OIDC로 IAM 역할 임시 획득 (GitHub에 AWS 키를 저장하지 않음)
                    2. 보안 그룹에 "러너 IP → 22번" 규칙 추가
                    3. SSH → git pull → docker compose up --build -d → /ping 헬스 체크
                    4. 규칙 삭제 (실패해도 always()로 반드시 삭제)

EC2 (t3.micro, Ubuntu 24.04, ap-southeast-2)
  └─ Docker Compose: app(Spring Boot) + mysql(볼륨 mysql-data), restart: unless-stopped
```

- **리전**: AWS 무료 플랜 프로젝트가 시드니(ap-southeast-2)에 고정되어 있어 서울 대신 시드니에 배포.
  한국에서 왕복 지연이 약 0.1초 늘어나지만 포트폴리오 데모에는 영향 없음.
- **22번 포트를 평소에 닫아 두는 이유**: GitHub 러너 IP는 매번 바뀌어 고정 IP로 허용할 수 없음.
  22번을 전체(0.0.0.0/0)에 여는 방법은 간단하지만 상시 공격 대상이 되므로, 배포하는 동안만 러너 IP 하나를 연다.
- **권한 최소화**: 배포 역할은 이 저장소의 `main` 브랜치에서만 맡을 수 있고(`sub` 조건, GitHub 계정·저장소 고유 ID 포함 형식), 할 수 있는 일은
  이 보안 그룹 하나에 인바운드 규칙을 추가·삭제하는 것뿐 (`infra/deploy-role-*.json`).
- **배포 전용 SSH 키**: 개발자 접속용 `.pem`과 분리. 유출 시 EC2의 `authorized_keys`에서 이 키만 지우면 됨.
- **메모리 1GB 대응**: 이미지 빌드(Gradle) 중 메모리가 부족해 스왑 2GB 추가.
  개선 방향: GitHub Actions에서 이미지를 빌드해 레지스트리(GHCR)에 올리고 EC2는 pull만 하도록 변경.

## 알고 있는 한계
1. 게임 쪽 미구현: 해달왕국은 현재 누적 획득 골드를 세지 않음. 연동하려면 골드 획득 시 누적값을 더하는 기능이 필요함 (팀 합의 필요).
2. 클라이언트 신뢰 문제: 점수를 클라이언트가 계산해서 보내므로 조작된 값을 막을 수 없음. MVP 범위 밖. 대응 후보: 제출 이력 기반 이상 증가 탐지 (결정 1-B).
3. 동시성: 결정 4 참고.
4. ~~사용자 식별: 요청에 `userId`를 직접 담으므로 남의 아이디로 제출 가능.~~ → **해결(11/10)**: `POST /scores`는
   `Authorization: Bearer <JWT>`의 `userId`만 사용하고, 요청 body에서는 `userId`를 받지 않음.
   body에 다른 `userId`를 넣어도 무시되고 토큰 주인의 기록으로 저장되는 것을 확인함.
5. ~~인증 실패 응답이 500.~~ → **해결(11/10)**: `GlobalExceptionHandler`에서 409/401/400 + `ErrorResponse(code, message)`로 통일.
   jjwt 예외는 `JwtTokenProvider` 안에서 `AuthenticationException`으로 바꿔 던짐(외부 라이브러리 의존을 한 파일에 가둠).
6. 퍼블릭 IP가 고정이 아님: 인스턴스를 중지 후 시작하면 IP가 바뀜(재부팅은 유지). 탄력적 IP나 도메인을 연결하면 해결.
7. 배포 중 짧은 중단: 같은 서버에서 컨테이너를 교체하므로 재시작 동안(수십 초) 요청이 실패할 수 있음. 무중단 배포는 범위 밖.
